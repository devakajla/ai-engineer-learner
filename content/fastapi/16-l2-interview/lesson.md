## 1. Dependency injection (lesson 8)

**Q: What is `Depends` in FastAPI, and why use it?**

**A:** It is FastAPI's built-in dependency injection. A route says what it needs (a database session, the current user, a service). FastAPI calls the provider functions for each request, and fills in their parameters too. It removes copy-paste (paging, login checks), lets you swap parts, and makes testing easy with `app.dependency_overrides`.

- *How many times is a shared sub-dependency called per request?* Once. The result is cached for that request (`use_cache=True`).
- *How do `yield` dependencies work?* Code before `yield` runs before the route. The yielded value is injected. Code after `yield` runs after the response. It is perfect for database sessions.
- *Where do you create the database engine and where the session?* The engine once per process (it owns the pool). A session for each request, from a dependency.

## 2. Databases (lesson 9)

**Q: `GET /orders?status=pending` became slow when the table grew to 10 million rows. How do you find and fix the problem?**

**A:** First reproduce it. Then run `EXPLAIN ANALYZE` on the query. Probably it does a full table scan. Add an index on `status`, or a composite index such as `(status, created_at)` that matches the filter and the sort. Make sure the endpoint is paginated with a bounded limit (a cursor for deep pages), and that it selects only the needed columns. Check for N+1 queries when building the response.

- *What does an index cost?* Slower writes and more storage. Choose columns based on your queries.
- *Explain ACID and isolation levels.* Atomicity, Consistency, Isolation, Durability. Isolation levels (read committed, repeatable read, serializable) trade away some strange effects (dirty reads, non-repeatable reads, phantom reads) for more concurrency.
- *How do you prevent SQL injection?* Parameterized queries, or the ORM's bound parameters. Allow only a fixed list of names for things like sort columns.

## 3. ORM (lesson 10)

**Q: What is the N+1 problem? How do you find it and fix it?**

**A:** You load N parent rows with one query, then a relationship is loaded lazily for each row. That is N extra queries. Find it with SQL logging (`echo=True`), query-count checks in tests, or tracing tools. Fix it with eager loading (`selectinload` for collections, `joinedload` for many-to-one), or with an aggregate query (`GROUP BY`).

- *Why can async SQLAlchemy not lazy-load?* It would need a hidden `await`. You must load relationships up front.
- *ORM or raw SQL?* ORM for normal CRUD (safe, portable). Raw SQL or Core for complex reports or hot paths.

## 4. Migrations (lesson 11)

**Q: How do you add a NOT NULL column to a big production table without downtime?**

**A:** Expand and contract. Add the column as nullable (or with a server default). Deploy code that writes it. Fill the old rows in small batches. Then add the NOT NULL rule. Remove the old code paths later. Run migrations before deploying the new code, and make them work with the old version that is still running.

- *What does `alembic_version` store?* The id of the database's current revision.
- *Why review autogenerated migrations?* A rename looks like drop and add (the data is lost), and some defaults and type changes are not detected.

## 5. Async (lesson 12)

**Q: When should a FastAPI route be `async def`?**

**A:** When everything slow inside it is awaited async I/O (an async database driver, `httpx.AsyncClient`, async Redis). A plain `def` route runs in a thread pool and is fine for blocking libraries. Never call blocking code in `async def`. It freezes the event loop for all requests. If you cannot avoid it, use `asyncio.to_thread`.

- *How do you call three services at the same time?* `asyncio.gather` or a `TaskGroup`, with timeouts (`wait_for`).
- *Does async help CPU-bound work?* No. Use processes or background workers.

## 6. Errors, middleware and logging (lesson 13)

**Q: How do you keep errors consistent across a big API?**

**A:** Services raise domain errors (`NotFoundError`, `ConflictError`). One place maps them to HTTP with `exception_handler` functions. The body has a stable shape: `detail` plus a machine-readable `code`. A catch-all handler for 500 logs the traceback and returns a generic message.

- *How do you follow one request through the logs?* Request-ID middleware, a `ContextVar`, and a log filter or record factory. Return the ID in a response header.
- *Is CORS a security feature?* It is a browser rule. It does not log anyone in, and it does not stop non-browser clients.

## 7. API design (lesson 14)

**Q: Offset or cursor pagination?** Offset is simple and allows random access, but deep pages are slow and it is unstable when rows are inserted. A cursor (keyset) uses the index and is stable, but has no random access.

**Q: A client's network dropped after `POST /payments`. How do you make the retry safe?** Use an idempotency key header. Store the key, the request and the response. Replay the saved response on a retry. Reject the same key with a different body. Use a unique constraint so two retries at once cannot both win.

**Q: What is a breaking change?** Removing or renaming fields, changing types, meaning or status codes, or adding a required input. Ship it as a new version and deprecate the old one.

## 8. Testing (lesson 15)

**Q: How do you test an endpoint that uses the database and an outside API?**

**A:** Write an integration test with `TestClient`. Override `get_db` with an isolated test database (a temp file, a rolled-back transaction, or testcontainers). Override the outside client with a fake that can also simulate timeouts and errors. Check the status, the **body**, and the side effects.

- *Is high coverage enough?* No. Tests must fail when behaviour breaks. Think "mutation testing".

## 9. Lifespan and docs (new lesson)

**Q: How do you run code at startup and shutdown?**

**A:** Pass a `lifespan` async context manager to `FastAPI(lifespan=...)`. Code before `yield` is startup (create the HTTP client, load a model), code after is shutdown (close them). Keep the objects in `app.state` and give them to routes through a dependency. `on_event` is deprecated.

- *Dependency with `yield` versus lifespan?* A dependency runs for each request. A lifespan runs once per app (per worker process).
- *Why does my test miss `app.state`?* `TestClient` runs the lifespan only inside `with TestClient(app) as client:`.
- *How do you make the docs useful?* Tags, summaries, `operation_id` (for client generators), `deprecated=True` for old routes. `include_in_schema=False` only hides a route, it is not security.

## 10. Database patterns (new lesson)

**Q: Two users buy the last item at the same time. How do you stop overselling?**

**A:** Do the check and the change in one SQL statement: `UPDATE items SET qty = qty - 1 WHERE id = :id AND qty > 0`, then check `rowcount`. Or lock the row with `SELECT ... FOR UPDATE`. An `if` in Python is not safe, because another request can run between the read and the write.

- *What is optimistic locking?* A `version` column. The save works only if the version is the one the client saw, and it adds 1. A clash gives `409`, and the client reloads. Nobody is locked out.
- *Where do you commit in a layered app?* In the service, so one business step is one transaction. Repositories do not commit.
- *How do you handle a duplicate email?* A `UNIQUE` constraint, catch `IntegrityError`, `rollback()`, raise `ConflictError` (`409`). Do not "check then insert".
- *How do you model many-to-many?* A link table with both foreign keys as the primary key, and `relationship(secondary=...)`.
- *What is the catch with soft delete?* Every query must filter the deleted rows, and unique rules must ignore them.

## 11. A small system design question

**Q: TaskFlow must handle 1,000 requests per second. What changes?**

A strong answer covers:

- stateless app copies behind a load balancer (each running several uvicorn workers),
- PostgreSQL instead of SQLite, with a sized connection pool (and PgBouncer) and indexes that match the queries,
- read replicas if reads dominate,
- caching hot reads (Redis),
- cursor pagination,
- background workers for slow jobs (emails, AI calls),
- rate limiting,
- observability: metrics such as p95 latency and error rate, plus tracing.

Then be ready for: *what would you measure first?*

## Tools for the three coding exercises

The three exercises are small tasks like you might get in a 25-minute interview. Here are building blocks, shown on **different** problems from the exercises.

**Plan first.** Before you type, say the rules out loud, list the status codes, and name the edge cases. Then code and test.

### Building block 1: turn a number into a short code (for the URL shortener)

To write a number in another base (like base 16 or base 62), divide by the base again and again. The **remainders** are the digits, from last to first. `divmod(n, base)` gives the division result and the remainder together.

```python
DIGITS = "0123456789abcdef"      # base 16

def to_hex(n):
    if n == 0:
        return DIGITS[0]
    out = ""
    while n > 0:
        n, remainder = divmod(n, 16)
        out = DIGITS[remainder] + out     # put the new digit in front
    return out

print(to_hex(255))   # -> ff
print(to_hex(16))    # -> 10
print(to_hex(1))     # -> 1
```

For base 62, use a longer string of digits. Test small numbers by hand first.

Other pieces for the shortener:

- **Idempotent create:** keep a dict `url -> code`. If the URL is already there, return the old code (with a different status code, like `200`) and do not make a new one.
- **A redirect:** return `RedirectResponse(url, status_code=307)`. Use `307` (the method is kept and the redirect is not cached forever), while `301` is "moved permanently" and browsers cache it, so your hit counter would stop counting.
- **A counter:** a dict `code -> hits`, and `hits[code] += 1` on each visit.
- Order the routes so that a fixed path like `/links/{code}/stats` is not swallowed by `/{code}` (lesson 3).

```python
from fastapi.responses import RedirectResponse

@app.get("/go/{name}")
def go(name: str):
    return RedirectResponse("https://example.com", status_code=307)

r = TestClient(app).get("/go/x", follow_redirects=False)
print(r.status_code, r.headers["location"])   # -> 307 https://example.com
```

### Building block 2: count the SQL queries (for the N+1 fix)

The tests count SQL statements. You can count them too, with an event listener on the engine:

```python
from sqlalchemy import event

queries = []

@event.listens_for(engine, "before_cursor_execute")
def count_query(conn, cursor, statement, parameters, context, executemany):
    queries.append(statement)
```

Run your code, then look at `len(queries)`.

Two ways to cut the queries (both from lesson 10):

- `select(User).options(selectinload(User.tasks))` loads all users and all their tasks in **2 queries**. Then work out the numbers in Python, for example `len([t for t in user.tasks if not t.done])`.
- One `GROUP BY` query that counts, plus one query that finds the latest task for each user.

With `selectinload`, "the latest task" is the one with the highest id in `user.tasks`: `max(user.tasks, key=lambda t: t.id)`. Remember a user may have no tasks, so check for an empty list first.

### Building block 3: a lock to stop a race (for no-overselling)

A **race condition** happens when two tasks check something, then both act on it, and the check is no longer true by the time they act. With `await` in the middle, other requests run in between.

Here is a race on a counter, and the fix:

```python
import asyncio

stock = 3

async def buy_unsafe():
    global stock
    if stock > 0:
        await asyncio.sleep(0.01)      # real I/O: other requests run here
        stock -= 1
        return True
    return False

async def main():
    results = await asyncio.gather(*(buy_unsafe() for _ in range(10)))
    print(sum(results), stock)         # -> 10 -7   (sold 10 of 3!)

asyncio.run(main())
```

The fix is an `asyncio.Lock`. Only one task at a time may be inside the `async with lock:` block. The check and the change become one safe unit:

```python
lock = asyncio.Lock()
stock = 3

async def buy_safe():
    global stock
    async with lock:
        if stock > 0:
            await asyncio.sleep(0.01)
            stock -= 1
            return True
        return False

async def main():
    results = await asyncio.gather(*(buy_safe() for _ in range(10)))
    print(sum(results), stock)         # -> 3 0

asyncio.run(main())
```

For many items, keep one lock per item in a dict: `LOCKS = {"tshirt": asyncio.Lock()}`.

Remember the limit: an `asyncio.Lock` works only inside **one process**. With several servers, let the database decide in one statement: `UPDATE stock SET qty = qty - 1 WHERE item = :i AND qty > 0`, and check how many rows changed. Or use an atomic Redis `DECR`.
